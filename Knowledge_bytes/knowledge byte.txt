CURRENT-ACCURACY NOTES (read this before anything else)
-------------------------------------------------------
* Order synchronisation is Java/Spring end to end:
      PostgreSQL -> RabbitMQ -> OrderSyncListener (@RabbitListener) -> Elasticsearch
  There is NO Celery anywhere in this repository. Indexing happens inside the
  Spring AMQP listener, in the same jar as the API.
* Elasticsearch is a disposable projection. PostgreSQL owns orders and users;
  MongoDB owns the product catalog. Elasticsearch owns no truth at all.
* The cart is client-side only (Pinia store in localStorage). The server never
  persists a cart; a cart only becomes real when POST /api/orders commits.
* The storefront walks results with an opaque cursor and an IntersectionObserver
  sentinel. There is no page-number UI on the storefront. Page parameters still
  exist on the API for compatibility, and the admin catalog screen still uses
  page numbers.

### Byte 1 — What Meridian actually is
Builds on: nothing (start here)
Files: README.md, docker-compose.yml, backend/src/main/java/com/meridian/backend/MeridianApplication.java
In plain terms: Meridian is a demo online shop with a Vue 3 front end and a Java Spring Boot API, backed by four different systems that each do one job.
Why it exists: You cannot learn the code until you know which box owns which fact.
How it connects: Every later byte is one corner of this picture.
The code:
```text
Browser (localhost:5173, Vue 3 + Pinia + axios)
   -> HTTP /api/** with a Bearer JWT
   -> Spring Boot API (localhost:8000)
        -> PostgreSQL   users, orders, order_items   (source of truth)
        -> MongoDB      products                     (catalog)
        -> RabbitMQ     queue orders_sync            (decoupling)
        -> Elasticsearch index "orders"              (search projection)
```
What to notice: Three stores plus a queue. Elasticsearch is a copy, not a source of truth.

### Byte 2 — Polyglot persistence and "one home per fact"
Builds on: Byte 1
Files: README.md (section 4), docker-compose.yml
In plain terms: Polyglot persistence means using several databases on purpose, each for the data it suits.
Why it exists: Orders need transactions and foreign keys; products need flexible nested fields; search needs an inverted index. One database would be worse at two of the three.
How it connects: Explains why OrderService writes to PostgreSQL while ProductService queries MongoDB in the same request path.
The code:
```text
PostgreSQL -> ACID, FKs, permanent order audit rows
MongoDB     -> products as documents: tags[], attributes{}, variants[]
Elasticsearch -> filters + aggregations over orders in milliseconds; rebuildable
RabbitMQ    -> separates "placing an order" (fast, durable) from "indexing" (may lag)
Filesystem  -> /app/uploads for admin-uploaded product images
```
What to notice: "Rebuildable" is the key word for Elasticsearch; if it is lost, the seeder and the listener can recreate it from PostgreSQL.

### Byte 3 — Spring Boot, MVC, controller/service/repository
Builds on: Byte 1
Files: MeridianApplication.java, products/ProductController.java, products/ProductService.java, products/repository/ProductRepository.java
In plain terms: Spring Boot starts a web server and wires your classes together (dependency injection). Spring MVC maps URLs to methods. The usual split is controller (parse HTTP), service (rules), repository (talk to storage).
Why it exists: Keeping HTTP parsing out of the service is what makes the rules testable without a server.
How it connects: ProductController -> ProductService -> MongoTemplate/ProductRepository is the pattern every feature follows.
The code:
```java
@SpringBootApplication(exclude = {MongoAutoConfiguration.class})
@EnableAsync
@EnableScheduling
public class MeridianApplication {
    public static void main(String[] args) { SpringApplication.run(MeridianApplication.class, args); }
}
```
What to notice: MongoAutoConfiguration is excluded on purpose — MongoConfig builds its own MongoTemplate, so Spring Boot's default Mongo beans are switched off.

### Byte 4 — DTO: the shape you send over the wire
Builds on: Byte 3
Files: products/dto/ProductListResponse.java, orders/dto/OrderResponse.java, application.yml
In plain terms: A DTO (data transfer object) is a plain class that exists only to serialise data into a JSON response or out of a JSON request. It is not a database row.
Why it exists: Entities carry database concerns (lazy loading, ids, timestamps); DTOs carry the public contract. Mixing them leaks internals.
How it connects: ProductDocument (Mongo) is mapped to ProductResponse (JSON); Order (JPA) is mapped to OrderResponse (JSON).
The code:
```yaml
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```
```java
public class ProductListResponse {
    private List<ProductResponse> items;
    private int page, limit, total, pages;
    private String nextCursor;   // serialises as "next_cursor"
    private boolean hasMore;     // serialises as "has_more"
```
What to notice: Java field names are camelCase; the JSON contract is snake_case because of that one YAML setting. Frontend code must ask for `data.next_cursor`, not `data.nextCursor`.

### Byte 5 — MongoDB document versus PostgreSQL row
Builds on: Byte 2, Byte 4
Files: products/document/ProductDocument.java, orders/entity/Order.java
In plain terms: A PostgreSQL row is a fixed set of columns enforced by a schema; a MongoDB document is a flexible JSON-like object where fields can differ per row.
Why it exists: Product attributes differ per category (a keyboard has switches, a mug has capacity), so a fixed column set would need a migration every time.
How it connects: ProductDocument carries attributes as Map<String,Object> and variants as a nested list — no join tables anywhere.
The code:
```java
@Document(collection = "products")
public class ProductDocument {
    @Id private String id;                       // Mongo ObjectId as String
    @Field("attributes")
    private Map<String, Object> attributes = new HashMap<>();
    @Field("variants")
    private List<Variant> variants = new ArrayList<>();
```
What to notice: `@Field("...")` pins the stored field name; the Java property name can differ from what is written to Mongo (this matters for cursor predicates — Byte 26).

### Byte 6 — MongoTemplate versus MongoRepository
Builds on: Byte 5
Files: products/ProductService.java, products/repository/ProductRepository.java, config/MongoConfig.java
In plain terms: A repository gives you named finder methods; MongoTemplate is the lower-level API where you build queries by hand.
Why it exists: Cursor pagination, combined filters and sort + range predicates are one query built at runtime — impossible to express as a fixed method name.
How it connects: ProductService uses ProductRepository for simple calls (findBySku, deleteBySkuIn) and MongoTemplate for the listing query.
The code:
```java
public class ProductService {
    private final ProductRepository productRepository;
    private final MongoTemplate mongoTemplate;
```
What to notice: Spring Data's derived queries are compile-checked convenience; MongoTemplate is where you accept responsibility for field names.

### Byte 7 — Elasticsearch: index, query, aggregation
Builds on: Byte 2
Files: search/repository/OrderSearchRepository.java, search/SearchService.java
In plain terms: An index is a searchable table-like collection of JSON documents. A query filters them; an aggregation summarises them (counts, sums).
Why it exists: The admin dashboard needs "revenue and counts by status" over thousands of orders instantly — a SQL GROUP BY over the OLTP table would also work, but the demo is showing a search engine doing it.
How it connects: The dashboard KPI cards are fed by one aggregation call, not by five queries.
The code:
```java
// OrderSearchRepository — builder style; one call returns hits AND aggregations
SearchRequest.Builder requestBuilder = new SearchRequest.Builder()
    .index(indexName)
    .query(query)
    .from(from).size(size);
requestBuilder.aggregations("revenue", a -> a.sum(s -> s.field("total_amount")));
requestBuilder.aggregations("status_counts", a -> a.terms(t -> t.field("status").size(10)));
return esClient.search(requestBuilder.build(), ElasticsearchOrderDocument.class);
```
What to notice: Aggregations are computed over the *whole* filtered set, not over the current page — that is why KPIs stay correct while you page.


### Byte 9 — JWT and BCrypt, in one breath
Builds on: Byte 1
Files: security/JwtTokenProvider.java, auth/AuthService.java, config/SecurityConfig.java
In plain terms: BCrypt hashes the password so the database never stores a password. A JWT (JSON Web Token) is a signed, self-describing pass you show on every request so the server needs no session.
Why it exists: Stateless servers scale horizontally; no session table, no logout bookkeeping on the server.
How it connects: Login verifies BCrypt and returns a JWT; JwtAuthenticationFilter validates that JWT on every later request.
The code:
```java
if (!passwordEncoder.matches(request.getPassword(), user.getPasswordHash())) {
    throw new NotFoundException("Invalid email or password", "invalid_credentials", null);
}
String accessToken = jwtTokenProvider.generateToken(String.valueOf(user.getId()));
```
What to notice: The token carries only the user id as subject — no role claim. The role is re-read from PostgreSQL per request (Byte 80).

### Byte 11 — IntersectionObserver, sentinel, infinite scroll
Builds on: Byte 10
Files: frontend/src/views/StorefrontView.vue, frontend/e2e/storefront-infinite-scroll.spec.js
In plain terms: Infinite scroll means more rows appear as you approach the bottom. IntersectionObserver is a browser API that tells you when an element enters the viewport, without polling on a timer.
Why it exists: A scroll listener would fire constantly and still need maths; an observer lets the browser decide.
How it connects: StorefrontView renders an empty sentinel div after the grid; when it enters a 600px band, the next cursor batch is requested.
The code:
```js
const SENTINEL_ROOT_MARGIN = '600px 0px'

observer = new IntersectionObserver(
  (entries) => {
    sentinelVisible = entries.some((entry) => entry.isIntersecting)
    if (sentinelVisible) loadMore()
  },
  { rootMargin: SENTINEL_ROOT_MARGIN },
)
if (loadMoreSentinel.value) observer.observe(loadMoreSentinel.value)
// the div carries data-testid="load-more-sentinel"
```
What to notice: The 600px band prefetches a batch before the user actually reaches the bottom, so the grid feels instant. The sentinel div is ALWAYS rendered (only its content toggles) so `observe` has one stable node across filter changes.

### Byte 15 — One authenticated GET, start to finish
Builds on: Byte 3, Byte 9
Files: config/SecurityConfig.java, security/JwtAuthenticationFilter.java, products/ProductController.java
In plain terms: A request passes a chain of filters (CORS, JWT), then Spring MVC finds the handler, validates its parameters, and calls it.
Why it exists: Authentication must happen before your controller code, otherwise every method would re-implement it.
How it connects: Knowing this order explains why a bad token is a 401 but a bad body is a 422.
The code:
```text
HTTP request
  -> CorsFilter / FilterChainProxy
  -> JwtAuthenticationFilter   (Bearer token -> SecurityContext user, or stays anonymous)
  -> UrlAuthorizationFilter    (permitAll / authenticated / hasRole rules)
  -> DispatcherServlet -> ProductController.listProducts(...)
  -> ProductService.listProducts(...) -> MongoTemplate
  -> Jackson writes snake_case JSON
```
What to notice: URL rules are checked BEFORE method-level `@PreAuthorize`, and body validation happens BEFORE the method-level check — Byte 240 shows the consequence.

### Byte 16 — SecurityConfig: the URL rule list, in order
Builds on: Byte 15
Files: config/SecurityConfig.java
In plain terms: Spring Security walks the matchers top to bottom and stops at the first one that matches.
Why it exists: It is a single readable list of what the internet may touch without a login.
How it connects: The list is only half the story; `@PreAuthorize` on controller methods is the other half (Byte 82).
The code:
```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()
    .requestMatchers("/api/health").permitAll()
    .requestMatchers("/api/products", "/api/products/facets").permitAll()
    .requestMatchers("/api/products/**").permitAll()          // matches everything below
    .requestMatchers(HttpMethod.POST, "/api/orders").authenticated()
    .requestMatchers(HttpMethod.GET, "/api/orders/**").authenticated()
    .requestMatchers(HttpMethod.PATCH, "/api/orders/*/status").hasRole("ADMIN")
    .requestMatchers("/api/search/**").hasRole("ADMIN")
    .requestMatchers(HttpMethod.POST, "/api/products").hasRole("ADMIN")   // never reached
    .anyRequest().authenticated()
)
```
What to notice: `/api/products/**` is permitAll and appears BEFORE the product hasRole rules, so those later rules are unreachable. The real write protection is `@PreAuthorize` — see Bytes 82 and 240.

### Byte 17 — CORS: one bean, one allowlist
Builds on: Byte 15
Files: config/WebConfig.java, .env.example
In plain terms: Cross-Origin Resource Sharing (CORS) is the browser's rule that http://localhost:5173 may not call http://localhost:8000 unless the server says yes. A preflight OPTIONS request asks first.
Why it exists: Without it, the browser blocks every API call even though the server would happily answer.
How it connects: A single `CorsConfigurationSource` bean is shared by the security filter chain and Spring MVC.
The code:
```java
@Value("${app.cors.allowed-origins:http://localhost:5173}")
private String allowedOrigins;
// WebConfig builds one CorsConfigurationSource with allowCredentials=true and
// allowedMethods GET/POST/PATCH/DELETE/OPTIONS, then marks the bean @Primary.
```
What to notice: The allowlist comes from `CORS_ORIGINS` in `.env`. WebConfig's own Javadoc explains that without this bean Spring would fall back to `HandlerMappingIntrospector`, which returns null and breaks preflight.

### Byte 18 — The error envelope
Builds on: Byte 4
Files: common/dto/ErrorBody.java, common/dto/ErrorResponse.java, exception/GlobalExceptionHandler.java
In plain terms: Every error body is `{ "error": { "code", "message", "details" } }`. The code is a stable machine string; the message is for humans.
Why it exists: Clients branch on `code`, users read `message`. One shape means one parsing path.
How it connects: `toApiError()` on the frontend reads exactly this envelope and turns it into an `ApiError`.
The code:
```json
{ "error": { "code": "invalid_cursor",
             "message": "The cursor is not a valid cursor token.",
             "details": { "field": "cursor" } } }
```
What to notice: Validation failures add `details.fields[]` with `field`, `message` and `type`. Two error bodies are hand-built outside this class — the 401 entry point and the 403 denied handler.

### Byte 19 — AppException: status codes as subclasses
Builds on: Byte 18
Files: exception/AppException.java, exception/NotFoundException.java, exception/UnprocessableException.java, exception/ConflictException.java, exception/DependencyUnavailableException.java, exception/OrderPersistenceException.java
In plain terms: Instead of sprinkling `ResponseEntity.status(...)` through services, services throw a typed exception and one handler maps it to a status.
Why it exists: Business rules stay in the service and remain testable without HTTP.
How it connects: `throw new UnprocessableException(msg, code, details)` becomes a 422 with that code.
The code:
```java
public class AppException extends RuntimeException {
    private final String code; private final int statusCode; private final Object details;
}
public class UnprocessableException extends AppException {
    public UnprocessableException(String message, String code, Object details) {
        super(message, code, 422, details);
    }
}
```
What to notice: 404=NotFound, 409=Conflict, 422=Unprocessable, 503=DependencyUnavailable, 500=OrderPersistence. Knowing the class tells you the status.

### Byte 20 — GlobalExceptionHandler: five handlers and one catch-all
Builds on: Byte 19
Files: exception/GlobalExceptionHandler.java
In plain terms: A `@RestControllerAdvice` class sees every exception thrown from any controller and converts it to a response.
Why it exists: Without it, exceptions become Spring's default whitelabel error page with an HTML body.
How it connects: It is the reason an `invalid_cursor` 422 looks identical to a `validation_error` 422.
The code:
```java
@ExceptionHandler(AppException.class)            // -> its own status + code
@ExceptionHandler(MethodArgumentNotValidException.class)  // -> 422 validation_error
@ExceptionHandler(HttpMessageNotReadableException.class)  // -> 400 malformed body
@ExceptionHandler(MethodArgumentTypeMismatchException.class) // -> 400 bad param type
@ExceptionHandler(Exception.class)               // -> 500 internal_error  [catch-all]
```
What to notice: Anything without an explicit handler falls into the catch-all and becomes a 500 — including `@PreAuthorize` denials and query-parameter constraint violations. That is measured, not assumed; see Bytes 240, 241 and 242.

### Byte 24 — User: the only table with a password
Builds on: Byte 5
Files: orders/entity/User.java, orders/repository/UserRepository.java
In plain terms: A user row holds identity (name, email), a BCrypt hash, and a role string.
Why it exists: Orders must reference a real account, and login needs one place to check credentials.
How it connects: `JwtAuthenticationFilter` loads this row on every request to get the role; `OrderService` attaches it to every order.
The code:
```java
@Entity @Table(name = "users", indexes = { @Index(columnList = "email", unique = true) })
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Integer id;
    @Column(name = "password_hash", length = 255, nullable = false) private String passwordHash;
    @Column(name = "role", length = 20, nullable = false) private String role = "CUSTOMER";
```

### Byte 34 — Two paging modes, one endpoint
Builds on: Byte 33
Files: products/ProductService.java
In plain terms: With no cursor the service skips `(page-1)*limit` rows (classic paging). With a cursor it starts exactly where the last batch stopped.
Why it exists: Existing clients keep working; the storefront gets stable streaming.
How it connects: `skip` is only applied when `decoded == null`, so the two modes never fight over the same query.
The code:
```java
Query findQuery = Query.query(combine(filterCriteria(...), must))
    .with(Sort.by(sortSpec.direction(), sortSpec.property())
        .and(Sort.by(Sort.Direction.DESC, "_id")))
    .skip(decoded == null ? (long) (page - 1) * limit : 0L)
    .limit(limit + 1);
```
What to notice: `page` is clamped (`page<1 -> 1`, `limit>100 -> 100`) inside the service as well as by controller annotations.

### Byte 35 — What a cursor actually contains
Builds on: Byte 33
Files: products/ProductCursor.java
In plain terms: A cursor is Base64url-encoded JSON holding "which query", "which sort", "where I stopped".
Why it exists: The server must be able to resume without server-side session state — the token carries everything.
How it connects: The frontend treats it as an opaque string and never opens it.
The code:
```json
{ "v": 1,
  "f": "3e9e7662b6b9f581",   // fingerprint of the query it belongs to
  "sf": "created_at",        // Mongo field being sorted on
  "sd": "desc",              // direction of that sort
  "idd": "desc",             // direction of the unique _id tie-breaker
  "sv": 1759276800000,       // last row's sort value (millis / number / string)
  "id": "6ac325481a2b..." }  // last row's _id — what makes ordering stable
```
What to notice: "Opaque" means the CLIENT must not parse it. Changing these field names is a breaking change precisely because servers and tests treat them as fixed.

### Byte 36 — Encode: last row becomes the next token
Builds on: Byte 35
Files: products/ProductCursor.java
In plain terms: Take the final row of the batch, read its sort value and id, JSON them, Base64url them.
Why it exists: The next request must resume strictly AFTER that row.
How it connects: `ProductService` calls this only when it fetched an extra row (`overflowed`).
The code:
```java
node.put("v", VERSION); node.put("f", fingerprint);
node.put("sf", spec.mongoField()); node.put("sd", spec.direction().isAscending() ? "asc" : "desc");
node.put("idd", "desc");
node.put("sv", value);   // Long / Double / String depending on field
node.put("id", last.getId());
return Base64.getUrlEncoder().withoutPadding().encodeToString(json.getBytes(UTF_8));
```
What to notice: `encode` returns `null` when the id is not a valid ObjectId or the sort value is missing — a null cursor means "no next batch", which is exactly how `has_more` stays honest.

### Byte 38 — Fingerprint: a cursor belongs to one query
Builds on: Byte 37
Files: products/ProductCursor.java, products/ProductService.java
In plain terms: A short SHA-256 of (sort, visibility, category, tags, q) travels inside the cursor and must match the current request.
Why it exists: Resuming a category-filtered walk with a different filter would silently skip rows.
How it connects: Change any filter and the previous cursor becomes invalid — the UI restarts instead.
The code:
```java
String joined = String.join("\u0000", sort, visibility, category, String.join(",", tags), query);
byte[] digest = MessageDigest.getInstance("SHA-256").join(...).digest(...);
return HexFormat.of().formatHex(digest, 0, 8);   // first 8 bytes -> 16 hex chars
```
What to notice: Only the first 8 bytes of the digest are used — enough to detect mismatch, short enough to keep the token tiny. This is integrity checking, not encryption; the payload stays readable.

### Byte 39 — Why every sort appends `_id DESC`
Builds on: Byte 34
Files: products/ProductService.java, products/SortSpec.java
In plain terms: Prices and titles repeat. Sorting only by price means 40 identical rows with no defined order, so paging through them skips or repeats.
Why it exists: A pagination cursor needs a totally ordered sequence; a unique id guarantees it.
How it connects: The tie-breaker is added to the Sort and to the continuation predicate, never to the public `?sort=` options.
The code:
```java
.with(Sort.by(sortSpec.direction(), sortSpec.property())
    .and(Sort.by(Sort.Direction.DESC, "_id")))
```
What to notice: `_id` is always DESC even when the primary sort is ASC — because ObjectIds are time-ordered, DESC keeps "newest first" as the secondary rule.

### Byte 40 — The continuation predicate: strictly after the cursor row
Builds on: Byte 39
Files: products/ProductService.java
In plain terms: Keep rows where the sort value is past the cursor's value, OR equal to it but with a smaller id.
Why it exists: That OR is what makes duplicates safe — it walks the tie-broken order, not just the value.
How it connects: It becomes one `$or` clause added to the same `$and` as the filters.
The code:
```java
Criteria tieBreaker = new Criteria().andOperator(
    Criteria.where(field).is(value),
    Criteria.where("_id").lt(new ObjectId(decoded.getId())));
Criteria primary = decoded.isAscending()
    ? Criteria.where(field).gt(value)
    : Criteria.where(field).lt(value);
return new Criteria().orOperator(primary, tieBreaker);
```
What to notice: `_id.lt(...)` uses a real `ObjectId`, not a string — comparing ids as strings would order them differently from Mongo's own `_id` order.

### Byte 41 — limit+1: how `has_more` is decided without a count
Builds on: Byte 34
Files: products/ProductService.java
In plain terms: Ask for one more row than you need. If it arrives, there is another batch; drop it and hand back a cursor.
Why it exists: A separate "is there more?" query doubles the work and can race with concurrent writes.
How it connects: `has_more` is derived from whether a cursor could be produced at all.
The code:
```java
boolean overflowed = documents.size() > limit;
if (overflowed) documents = new ArrayList<>(documents.subList(0, limit));

String nextCursor = overflowed && !documents.isEmpty()
    ? ProductCursor.encode(sortSpec, fingerprint, documents.get(documents.size() - 1))
    : null;
boolean hasMore = nextCursor != null;
```
What to notice: `has_more` can never be true with a null `next_cursor` — otherwise a client would poll forever with nothing to ask for.

### Byte 50 — Observing with a 600px lookahead

```js
  sentinelVisible = false
  observer = new IntersectionObserver((entries) => {
    sentinelVisible = entries.some((entry) => entry.isIntersecting)
```

### Byte 51 — loadMore: one request at a time
Builds on: Byte 50
Files: frontend/src/views/StorefrontView.vue
In plain terms: Do not start a second batch while one is running, and do not ask for a batch you cannot continue from.
Why it exists: Two in-flight appends are how duplicate rows and out-of-order UIs happen.
How it connects: `loading`/`loadingMore` are cleared in `finally` only if this request still owns the UI.
The code:
```js
async function loadMore() {
  if (loading.value || loadingMore.value) return
  if (!hasMore.value || !nextCursor.value) return
  await fetchBatch({ reset: false })
}
```
What to notice: Both flags are checked, not just one — a reset and an append can overlap for a moment when filters change mid-scroll.

### Byte 52 — fetchBatch: reset and append are the same code path
Builds on: Byte 51

In plain terms: One function fetches either the first batch (clearing state) or the next batch (appending).
Why it exists: Two paths drift; one path is testable once.

The code:

```js
  if (!reset && nextCursor.value) params.cursor = nextCursor.value
  // ...
  products.value = { ...data,
    items: reset ? (data.items || []) : [...products.value.items, ...incoming] }
```

What to notice: `has_more` is trusted only when a cursor accompanies it — the same rule the server guarantees (Byte 41), enforced again client-side.

### Byte 74 — pick(): same product, same picture, every run

### Byte 200 — Flow 15/40: Order created → queued → indexed (the core async path)

In plain terms: `createdAt` in Java is `created_at` in Mongo; `BigDecimal` in PostgreSQL is `Double` in Elasticsearch.
Why it exists: Each store's mapping conventions differ from Java's.
How it connects: Querying Mongo with the wrong name silently returns zero rows rather than an error.
The code:
```java
@Field("created_at") private OffsetDateTime createdAt;   // Java: createdAt  |  Mongo: created_at
@Column(precision = 12, scale = 2) private BigDecimal totalAmount;   // truth
@JsonProperty("total_amount") private Double totalAmount;            // projection (ES)
```
What to notice: Sort fields are declared once in `SortSpec.mongoField` to keep the literal name in one place — but only for the four sort keys.

### Byte 247 — Gotcha 9: order ids never rewind
Builds on: Byte 68
Files: SeedRunner.java
In plain terms: PostgreSQL's identity sequence keeps advancing across seed runs, so a second demo seed starts at a higher id than the first.
Why it exists: Sequence increments are not rolled back by deleting rows.
How it connects: Elasticsearch ids are stale after a reseed — which is why `recreateIndex()` runs BEFORE bulk indexing (Byte 68).
The code:
```text
first orders after reseed: id 343, 344, 345 ...   (measured 2026-10-05)
stale ES doc with _id=2 would survive if the index were not recreated
```
What to notice: `order_number` (`ORD-%000343`) follows the id, so reseeding changes numbers too — any bookmarked order URL from a previous run will 404.

### Byte 248 — Gotcha 10: security posture caveats
Builds on: Byte 79
Files: application.yml, .env.example, SecurityConfig.java, stores/auth.js
In plain terms: Four deliberate demo shortcuts that would need changing in production.
Why it exists: Convenience beats ceremony in a teaching repo — but the trade-offs should be stated.
How it connects: Each maps to a section of this document for the detail.
The code:
```text
1. default JWT secret in source   -> app.jwt.secret falls back to "change-me-in-production-..."
2. token in localStorage          -> readable by any script on the page (Byte 88)
3. GET /api/users is permitAll    -> exposes the 9 seeded accounts (names/emails/roles) to anyone
                                    (and no frontend component ever calls it)
4. CORS allowCredentials=true     -> fine with an explicit origin allowlist; dangerous with "*"
```
What to notice: Numbers 1 and 3 are the ones to fix first; 2 is a well-known SPA trade-off; 4 is currently safe because the allowlist comes from `CORS_ORIGINS`.
